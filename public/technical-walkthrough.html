BEGINNER-FRIENDLY PROJECT GUIDE

How Daymark works

A guided tour of how the task screen, API, database, local AI assistant, and deployment pieces fit together. You do not need to know every framework detail to follow the flow.

Start with this picture: Angular draws the page in your browser. It sends requests to a Spring Boot API. The API reads and saves data in PostgreSQL. For AI chat, the API also uses a message queue and a locally running Ollama model.

01 · SYSTEM MAP

The big picture

1. BrowserYou use the task list and chat.
2. Angular frontendShows the UI and sends HTTP requests.
3. Spring Boot APIChecks requests and runs application rules.
4. PostgreSQLKeeps tasks, conversations, messages, and proposals.
Chat-only supporting services: Spring Boot puts longer AI work in ActiveMQ Artemis → the separate ai-worker consumes a generic prompt job and calls Ollama privately → the worker publishes a correlated result to the caller's reply queue → Spring saves the task-chat result in PostgreSQL. The browser asks the API for updates while the job runs.

These are separate processes, but they work as one application. The browser does not connect directly to PostgreSQL, Artemis, Ollama, or the AI worker; it communicates with the API. The AI worker has no generation HTTP endpoint: service-to-worker AI requests use MQ.

02 · WHAT YOU SEE

The Angular frontend

The frontend is a single-page Angular application. Its root component is the workspace: it loads tasks and chat conversations when the page starts, stores the current screen state, and responds to clicks and form submissions.

Who does what?

  • AppComponent (src/app/app.component.ts) handles form events, loading and saving state, task editing, chat selection, polling, and action confirmation.
  • app.component.html describes the screen. Angular bindings put current data on the page and connect buttons/forms to component methods.
  • TaskService and ChatService (src/app/*.service.ts) are the HTTP clients. Keeping API calls here separates network work from screen layout.
  • task.model.ts and chat.model.ts describe the data shapes TypeScript expects from the API.
  • app.config.ts registers Angular's HTTP client; main.ts starts the standalone root component.

Forms use Angular reactive forms, which means their values and validation rules are managed in TypeScript. For example, a task title is required and has a 200-character limit before the request is sent.

03 · EXAMPLE REQUEST

What happens when you add a task?

  1. You enter a title and optional description in the task form.
  2. AppComponent.saveTask() checks the form and asks TaskService.createTask() to send the data.
  3. The service sends POST /api/tasks. In development Angular proxies /api to the backend; in Docker Nginx forwards /api/ to the backend service.
  4. TaskController receives the HTTP request and validates the input. It delegates the work to TaskService.
  5. TaskService uses TaskRepository (Spring Data JPA) to save a Task row in PostgreSQL.
  6. The API returns the saved task, including its generated ID and creation time. Angular adds it to the visible list.

Task endpoints

RequestPurpose
GET /api/tasksLoad all tasks
POST /api/tasksCreate a task
PUT /api/tasks/{id}Replace the editable fields of a task
DELETE /api/tasks/{id}Delete a task

Task data is represented by a database entity (Task), a validated request (TaskRequest), and a response shape (TaskResponse). These separate roles help keep database details and API input/output clear.

04 · ASYNC CHAT

How the local AI chat works

Chat has more steps than a normal task request because generating a response can take time. The queue lets the API acknowledge the message while a worker handles model processing separately.

  1. The browser sends a message to POST /api/chat/conversations/{id}/messages. The API saves the user's message as PROCESSING.
  2. For a recognizable read-only task question (for example, asking which tasks are unfinished), TaskQueryResponder can answer directly from the current task list without calling the model.
  3. Other messages are published to the Artemis queue. The API returns the processing message to the browser so the UI can stay responsive.
  4. The backend builds a prompt from recent conversation history and the current tasks, then sends a generic job containing messages, a response schema, a reply-queue name, and caller metadata. The separate ai-worker consumes it from Artemis and calls Ollama; the worker does not connect to PostgreSQL or know task-specific rules.
  5. Ollama returns content matching the supplied schema. The worker publishes that content with the correlation ID and metadata to the requested reply queue. The backend consumes the result, validates and saves the assistant reply and proposals. Angular polls message history until processing is finished.
The assistant cannot silently change your task list. It can propose a create, update, or delete action. Each proposal starts as PENDING. You choose Confirm change or Decline; only confirmation calls the task service to make the change.

Why proposals can be rejected

For an update or deletion, the backend compares the task with the snapshot recorded when the proposal was created. If someone changed that task in the meantime, confirmation returns a conflict rather than overwriting newer data. A proposal can also be resolved only once.

If model processing fails, the worker retries the job up to three attempts; a job that still fails is moved to the request dead-letter queue and a failure result lets the backend mark the chat message failed so the UI can show an error. The worker processes one job at a time, and Ollama's parallel-request setting defaults to one. This reduces concurrent load but does not cap the CPU used by one inference.

Before sending a prompt to Ollama, the worker adds the current weekday, date, time, timezone, and UTC offset. The default timezone is Asia/Kolkata; change it with AI_TIME_ZONE. This gives the model a fresh reference for basic date/time questions, though it does not make model-generated date arithmetic guaranteed.

Future services can publish their own prompt jobs to the same request queue and choose an ai.responses.<service> reply queue. The worker only accepts MQ jobs and has no HTTP generation port.

05 · API AND DATA

How the Spring backend is organized

The backend is a Java 21 Spring Boot application. A simple way to read a request path is:

HTTP request
    ↓
Controller  — maps a URL to a Java method
    ↓
Service     — applies rules and coordinates work
    ↓
Repository  — reads/writes entities through JPA
    ↓
PostgreSQL  — persists the data

The task code lives under backend/src/main/java/com/example/taskmanager/task. Chat code is under the neighboring chat package. Spring discovers components such as controllers, services, and repositories from the main application package.

Chat conversations, chat messages, and proposed actions have their own entities and repositories. Their records are stored in the same PostgreSQL database as tasks, so a reply and its action proposals can be loaded again later. Only the core backend accesses PostgreSQL; the AI worker receives generic prompt data and returns generated content without needing to know about tasks or databases.

Database connection, model URL/name, broker connection, and queue names are configured in backend/src/main/resources/application.properties and supplied through environment variables in Docker Compose. Keep real passwords in a private local .env file or a CI credentials store, not in source code.

06 · BUILD AND RUN

How Docker and Jenkins fit in

Docker Compose: run the whole application

docker-compose.yml defines the frontend, backend, PostgreSQL, Ollama, and Artemis containers. Services find one another by Compose service name on a private network. The frontend is exposed at http://localhost:8080; the database and model runtime are not published as public application endpoints.

  • The frontend Dockerfile first builds Angular with Node, then serves the built static files with Nginx.
  • nginx.conf serves those files and forwards /api/ requests to the Spring backend.
  • backend/Dockerfile packages the Spring application and runs it in a Java runtime container.
  • Named volumes preserve PostgreSQL data, downloaded Ollama models, and Artemis data between container rebuilds.
Copy-Item .env.example .env
# Set private values in .env, then:
docker compose up --build -d

Jenkins: repeatable deployment

Jenkinsfile describes the pipeline: check Docker/Compose, validate configuration, build the frontend and backend images, deploy with Compose, then check that the task API responds. Jenkins injects database and broker secrets from credentials instead of hard-coding them in the pipeline.

docker-compose.jenkins.yml starts the Jenkins controller for a local learning setup. It is separate from the application Compose file. The deployment and setup details are in JENKINS-DEPLOYMENT.md and BUILD-DEPLOYMENT.md.

08 · QUICK GLOSSARY

Plain-English terms

Frontend The code that runs in the browser and draws the page.

Backend The server-side application that applies rules and provides the API.

API The agreed set of URLs and data formats used by the frontend and backend to communicate.

HTTP The request/response protocol used for calls such as GET (read), POST (create/send), PUT (update), and DELETE (remove).

Entity A Java object that JPA maps to a database table.

Repository A data-access helper; Spring Data provides common database operations.

Queue A holding place for work that can be processed after the original request has returned.

Container A packaged process with its own runtime and dependencies. Docker Compose connects multiple containers.
